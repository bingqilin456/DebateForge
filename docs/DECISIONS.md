## ADR-001 后端采用 Gin 的模块化单体

状态：规划采纳，待对应任务实施前人工审查。

背景：原申报书倾向 go-zero，A 已有 Gin 经验，团队需兼顾课程、竞赛及技术学习，业务规模为认证、辩论和历史。优先降低学习、联调和排错成本。

| 方案 | 收益 | 本项目代价 |
| --- | --- | --- |
| Gin 模块化单体 | 复用现有经验，路由与中间件直观，便于追踪完整请求 | 需明确补齐超时、限流、日志、权限、健康与测试，不能把框架等同于生产保障 |
| go-zero 单体 REST | 有代码生成及较完整的工程治理约定，也可只用 REST 层 | 当前需额外学习 goctl、生成代码及配置习惯，收益暂不足以覆盖切换成本 |
| Go 标准库 net/http | 依赖少，控制明确 | 需自行统一路由和工程约定，较难复用 A 的现成 Gin 经验 |

决定：使用 Gin，按 auth、topic、debate、ai 模块组织单个进程，Eino 与框架解耦。Gin 提供路由和中间件机制，go-zero 提供代码生成及治理能力；二者都不能替团队完成业务验收。[Gin 中间件文档](https://gin-gonic.com/en/docs/middleware/)、[go-zero 官方文档](https://go-zero.dev/)

理由是团队熟悉度和 MVP 的交付成本，不是未经测量的性能优劣；也不将 go-zero 等同于必须采用微服务。责任是把必要中间件、事务和异常测试写清并执行。只有后续出现真实服务拆分或统一生成工具需求，且有测量与维护收益时才重新评估，不同时维护两套后端框架。

## ADR-002 前端采用 Vue 3 TypeScript Arco Design

状态：规划采纳，待对应任务实施前人工审查。

沿用项目方向与用户初步技术方案，配合 Vue Router、Vite 和统一 API client。优先用成熟表单、列表和反馈组件；不搭建设计系统、SSR 或动态菜单生成平台。当前页面少，局部状态与轻量共享登录状态足够，暂不强制加入 Pinia。

B 主责辩题与历史页面，A 主导复杂聊天和流式交互。收益是任务可拆分，代价是双方仍需学习 TypeScript、HTTP 和组件状态；不能沿用原申报书“团队已具备扎实 Vue 经验”的陈述。版本组合与必要的测试工具在 T01 核实锁定。

## ADR-003 Eino 仅用于单模型对话

状态：框架方向为规划采纳；不做复杂 Agent 为约束确定。

先使用 ChatModel 完整响应，保留流式适配边界，不引入 Agent Runner、工具调用、RAG、向量数据库或微调。Eino 组件已提供完整及流式响应能力，无需为三轮串行对话创建自主决策循环。[Eino ChatModel 文档](https://www.cloudwego.cn/zh/docs/eino/core_modules/components/chat_model_guide/)

由业务 Service 控制上下文、轮数和数据库，模型只生成内容。供应商通过后端配置指定，采用一个可验证的供应商和模型；不做自动故障切换。代价是供应商故障会使当次生成失败，需要清晰重试入口。具体供应商、模型、额度及输入窗口待确认，不能假设所有“兼容 API”均完整支持结构化输出或流式格式。

## ADR-004 MySQL 与 GORM 并使用版本化迁移

状态：规划采纳，待对应任务实施前人工审查。

采用 MySQL InnoDB 作为开发集成及生产持久化数据库，GORM 负责数据访问；初始表和后续变更用可审查的版本化 SQL，不在生产启动时 AutoMigrate。依靠短事务、外键及唯一索引保证会话、轮次与消息一致，模型调用放在事务之外。[GORM 事务文档](https://gorm.io/docs/transactions.html)

实体为 users、auth_sessions、topics、debates、debate_turns、messages、debate_summaries。独立轮次表用于失败、幂等和恢复，比只保存一段聊天文本多一张业务表，但让状态与消息可测试；不再引入单独任务系统或事件存储。数据库设计与 API 的唯一契约见 [ARCHITECTURE](ARCHITECTURE.md)。

## ADR-005 同源 Session 认证

状态：规划采纳，待对应任务实施前人工审查。

在单域名、单服务场景使用 MySQL 存储 Session，生产使用 Secure/HttpOnly/SameSite Cookie；随机 token 的哈希入库，退出能立即失效。密码采用成熟 Argon2id 实现。配置独立 CSRF token 和 Origin 校验；不把 Cookie 属性当作全部 CSRF 防线。[OWASP Session 指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

相比 JWT 加 localStorage，这个方案减少浏览器持有可读登录凭据、刷新 token 和吊销列表的工作；代价是请求需查询 Session，需清理过期记录。小规模单体可接受，不为 Session 单独引入 Redis。MVP 不做找回密码和邮件验证，开放范围需结合资源与风控确认。

## ADR-006 普通 JSON 优先 SSE 可选

状态：JSON 优先与后置 SSE 为规划采纳；SSE 非必须来自用户允许。

先验收“鉴权 → AI → 落库 → 展示”的完整响应，在 Phase 3 满足核心门槛且有余量时再选做 SSE。使用带 POST body 的 fetch 消费 SSE 格式，沿用原发送与重试接口；总结继续使用完整 JSON。SSE 为单向流，代理缓冲必须单独处理。[MDN SSE 文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)、[Nginx 代理文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

成功以最终落库为准，断线先查状态，失败才人工重试，不实现事件重放。收益是交付更早、失败路径更简单；代价是第一版有等待时间，需要明确 loading 和超时反馈。若增强未通过代理与断线验收，则关闭 SSE，不拖累 P0。

## ADR-007 三轮业务和总结独立

状态：三轮为约束确定；其余为规划采纳。

用户先发言，AI 持相反立场，完整 AI 回复落库才完成一轮；第 3 轮后辩论 completed。总结用单独请求和状态，前端自动发起、服务端幂等，失败可单独重试。采用 strengths、issues、suggestions 三类结构，不做分数和胜负判定。

相比第三轮和总结串成一次长请求，该方案减少超时后状态不明的问题，也不需常驻任务队列。代价是前端要展示独立总结状态，用户离开页面后可能待下次打开才触发总结。已保存辩论不受总结失败影响。

请求标识、唯一索引、短事务、attempt_version 和过期恢复共同保证数据库结果不重复。2026 年 11 月 1 日审查后，用户授权补齐轮次与总结重试契约：采用 expected_attempt_version，在短事务内仅允许匹配的失败版本认领一次；旧版本请求遇到再次失败返回 409，不重新调用模型，前端也不自动换版本重发。该方案复用现有版本字段，不增加重试表；代价是查询及错误响应须提供当前版本。它们不提供供应商“恰好调用一次”保证，不以隐式自动重试掩盖错误或费用。

## ADR-008 单机 Compose 部署与基本运维

状态：Linux/真实部署/HTTPS/持久化为约束确定；具体部署形态为规划采纳。

使用单台 Linux、Docker Compose、Nginx、单个 Go 实例和 MySQL 持久化卷；公网只暴露 Web 端口。首次公网开放前完成 HTTPS、日志、健康路由、认证限流、输入与生成限额、模型并发/超时及供应商硬预算检查，再完成基本告警、异机备份和独立库恢复；不引入 Kubernetes、集群可用性和监控平台。

收益是两人能理解并维护完整链路，代价是单机存在故障停机窗口、进程内限额重启丢失，不承诺高可用。2026 年 11 月 1 日审查后，用户授权把防刷与费用检查前移到 T07 之前，T13 仅做回归与调优；健康端点明确为 `/health/live`、`/health/ready`，由 Nginx 精确代理到 Go 并保留状态与 JSON，不走 SPA 回退。使用供应商硬费用上限和单实例限制控制风险；代价是 Phase 1 工作量增加，未完成检查则推迟公网开放。部署、备份和恢复的实际操作仍须用户明确授权，Phase 0 的 PB 不执行。

## ADR-009 Project Bootstrap 独立验收

状态：2026 年 11 月 1 日用户明确批准，技术验证及人工门槛见 [INIT_ACCEPTANCE](INIT_ACCEPTANCE.md)。

背景：T02 同时包含数据库，T06 包含登录和首轮辩论；直接照表实施会超过本轮授权。因此拆出 PB 作为 T01/T02/T06 的前置任务，不改变 PRD 的最终 P0。

决定：Go 模块路径为 `github.com/bingqilin456/DebateForge/backend`；使用 Go 1.27.1、Node.js 24.11.1、npm 11.6.2，前端只保留 package-lock.json。健康接口仅 `GET /health/live`，固定 alive JSON；`/health/ready` 留待真正接入 DB，不返回伪造 ready。后端默认 `127.0.0.1:8080`，HTTP_ADDR 限定回环地址和有效端口；Vite 在 `127.0.0.1:5173` 原样代理 `/health/`、`/api/`。不增加 CORS、数据库、模型、认证或部署配置。

单页面只使用局部状态、原生 fetch、Arco 的反馈组件；Vue Router 留待多页面，Pinia 与 Axios 暂不引入。使用 Vitest 测试客户端在真实临时 HTTP 服务下的行为，不增加组件测试框架或浏览器测试依赖；真实浏览器验收使用现有浏览器工具。代价是完整业务接口和页面路由仍待后续任务。

版本从官方 npm Registry / Go 模块代理及随包元数据核对后精确固定，见 README 依赖表。TypeScript 选择成熟的 5.9.3，而非直接升级到新主版本；实际组合仍通过类型检查、测试和构建验证，不以 peerDependencies 满足替代运行证据。

替代方案：一次执行完整 Phase 1 会越过 PB 范围；临时聊天接口会造成后续迁移；无数据库却固定 ready=200 会掩盖依赖状态，均不采用。用户禁止 commit、push、合并；“保留并提交锁文件”在本任务解释为保留可审查文件，实际提交等待单独授权。

## ADR-010 按阶段目标推进

状态：2026 年 11 月 2 日用户明确要求采用阶段制；本轮文档调整待人工审查，不是后续业务实施授权。

背景：团队需兼顾课程、ACM 训练和实验室考核，并边学习边实践。固定周次与投入假设无法表达暂停和技术阻塞，容易把赶进度误作验收。

决定：采用 Phase 0（PB）、Phase 1（T01–T07）、Phase 2（T08–T12）、Phase 3（T13–T15）、Phase 4（T16–T18），各阶段不限定自然日数或固定投入时长；保留原任务依赖、S/M/L、人时、P0/P1 和独立验收。阶段内在依赖满足后可并行，支持暂停、恢复和分工调整。当前必要 P0、阶段人工审查及下一阶段授权全部具备后才继续。

替代关系：原四周排期、固定投入假设及旧周次安排不再适用；原“Phase 0 规划审查”是 PB 之前的历史活动，旧 W1–W4 仅作为历史标签分别对应新 Phase 1–4。[INIT_ACCEPTANCE](INIT_ACCEPTANCE.md) 是既有技术证据，保持原样，不因重命名而成为人工验收通过记录。PB 保持待人工验收，T01–T18 的业务范围未开始。

替代方案：保留固定周表仅延长日期，仍会产生追赶压力；取消估算与门槛，则丢失工作量参考与质量控制，均不采用。

后果：完成时点随实际投入变化，超出估算不降验收标准；任务阻塞记录恢复条件，可转做当前阶段其他满足依赖的任务。真实模型、持久化、用户隔离、安全与预算前置、获准部署、备份恢复及答辩门槛均保留；SSE 仍为可取消 P1。阶段计划调整不授权提交、推送、合并、购买或部署。
