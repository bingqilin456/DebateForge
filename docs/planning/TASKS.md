## 分工、估算与依赖规则

自 2026-11-16 负责人确认起，采用**一功能一负责人端到端交付**：本文件「负责人」栏是当前任务归属的唯一事实来源，规则入口见 [PLAN 现行功能分工原则](PLAN.md#现行功能分工原则)，决策见 [ADR-026](../decisions/DECISIONS.md#adr-026-功能负责人端到端交付)。每项任务由单一功能负责人统筹该功能的前端、后端、测试及必要文档，可跨前后端实施；负责人须交付明确完整的功能并理解其完整链路，不按前后端固定人员边界限制改动范围，也不把任一成员缩窄为只跑测试、只排版或只整理材料。

功能负责人默认独立推进需求理解、前后端实现、测试、排错与必要文档，不将每个功能预拆成两人接力；B 可独立修改后端，A 可独立修改前端。表中协作职责均为按需支持，只在具体困难或共享核心风险需要时介入，不要求另一成员逐项参与或签字。A 对认证、持久化、生成认领、费用与部署按需提供技术支持与风险把关，不构成日常改动的审批门槛；项目负责人验收与高风险操作授权要求不变。共享状态机、迁移编号与公共接口契约同一时间由一名负责人统筹，修改前先约定文件范围与接口边界，避免并发编辑同一文件或争用同一迁移号；架构分层（Handler/Service/Repository）不变。可因课程、考试或竞赛调整功能负责人，并在对应任务行记录交接与新归属。已实现任务保留原 A/B 贡献描述，不重排历史、不伪造完成或签收；未开始的 P1 任务不因本次分工调整自动获得实施授权。

S 为低复杂度，约 1–3 人时；M 为中复杂度，约 3–6 人时；L 为较高复杂度，约 6–10 人时，应按子边界小步交付。人时是开发、学习、AI 输出理解审查与验证的粗略工作量估算，不是自然日或完成期限；不要求成员固定投入时长，实际投入可灵活调整，超出估算不降低验收标准。协作时间单列，不把两人并行视为零成本；原 T01–T18 的复杂度与估算保留。PB 原来未估工，本次只粗估剩余人工审查与讲解，不追填已发生工时。

所有任务均须满足所属阶段的前置门槛及授权范围。表中列明任务依赖与联调条件；只要依赖满足，可在阶段内选择独立任务或分工并行，不要求按编号依次完成。并行组 P-A 为契约后的基础模块，P-B 为核心闭环，P-C 为质量工作；同一成员的实际投入、共享文件和 API 变更必须协调。提前准备限于已确认契约下的页面、测试场景或文档，不跳过真实联调和独立验收，也不据此跨阶段扩大实施。功能负责人之外的成员可提供技术支持或风险把关，不因此改变该任务的负责人归属。

### T07-COST-01 供应商硬预算缺失

## 暂停与恢复

允许因课程、考试或竞赛暂停，或暂时搁置技术阻塞任务；保留已验收成果、在途改动及证据，不清零或强制追赶。恢复时仅检查当前 Phase、已完成且通过验收的任务、进行中/待人工验收任务、未解决阻塞、下一项满足依赖和授权的任务。负责人调整同步交接记录；环境或契约变化时重验受影响项。

## 任务执行模板

Phase 2（T08–T12）具体执行细则与 Spec 模板见 [Phase 2 轻量 SDD 工作流](PHASE2_SDD_WORKFLOW.md)：

1. **Spec 确认与契约对齐**：按需读取相关 PRD、架构与上游契约，核对阶段门槛、任务依赖、工作区和授权范围。编码前在 `docs/planning/Txx_<SLUG>_SPEC.md` 明确本任务增量边界、状态转换与验收矩阵；涉及 Phase 2 草案接口落地时同步晋升至 [API](../api/API.md) 与 [OpenAPI](../api/openapi.yaml)。
2. **测试先行（RED）**：先明确输入、输出、权限、状态、失败路径与测试并观察预期失败；业务风险用 Fake 或隔离 MySQL 验证，文档或样式改动只做对应检查。
3. **最小交付与分片推进（GREEN）**：实现最小交付，按改动影响范围运行相关定向测试、类型/构建和真实联调，直接复用未受影响的既有证据，不做无关全量复跑或无意义复验。L 任务按 Spec 子切片（Slice）小步验证（例如 T09 分三轮规则、重试并发、崩溃恢复），不为覆盖率堆测试。
4. **CI 基础门禁与专项验收**：由 [.github/workflows/ci.yml](../../.github/workflows/ci.yml) 守住静态规范、单测、隔离 MySQL 集成及前端构建等基础质量；完成必要的自动化测试及相关高风险专项验证，在 `docs/acceptance/Txx_<SLUG>_ACCEPTANCE.md` 简明记录文件范围、环境、命令与结果、未执行项和遗留问题。验证完成后仅在本文件置“待人工验收”，经项目负责人确认后置“已完成”；不要求 A/B 互审、正式契约讲解登记或强制重复独立审查，不另加其他成员互签要求，不再向多份顶层文档叠加状态快照横幅。
5. **授权边界**：未经明确授权不 commit、push、合并或部署。任务完成不自动进入下一阶段；阶段末报告验证结果、遗留问题及下一阶段前置条件，等待负责人确认。

## 责任不能转交给 AI

功能负责人在实施中须理解自己负责功能的完整链路。后端相关功能至少涵盖 Handler/Service/Repository、数据库唯一约束、短事务、attempt_version、Eino 上下文、超时、权限与恢复；前端相关功能至少涵盖组件状态、props/事件、API 请求、登录失效、分页与失败提示。谁负责该功能，谁就负责其前后端与测试证据，不因成员原属前后端而转移责任。两人共同理解**赛制语义（`debates.mode` 为唯一事实来源、`standard_4` 与 `quick_3` 的轮数差异、第 3 轮环节分叉）**、数据归属和上线风险，答辩按实际负责功能讲解。

如某成员可投入精力下降，按[现行功能分工原则](PLAN.md#现行功能分工原则)在对应任务行调整负责人并记录交接，保留其已交付功能与模块理解，先约定共享状态机、迁移编号与契约边界再移交；不能把任一成员的技术贡献压缩为只运行 AI 命令或准备演示文稿。
