# Codex 团队协作实战教程

> 面向 2～3 人的小型项目团队｜适用于 Go 后端、Vue 前端与 AI Agent 项目  
> **方法：轻量级 Harness Engineering + 规格驱动开发（SDD）+ 小步迭代 + Git 分支/PR + 自动化测试。**  
> 阅读方式：**第 1～6 节是每位队员的必修内容**；第 7～10 节用于团队约定与长期复用。文中「思弈阁 Lite」仅作为示例，可替换为其他项目。

## 0. 一页速览：怎么与 Codex 正确协作？

**核心分工：人负责需求、架构决策、验收和风险控制；Codex 负责在明确边界内分析、编写、修改、测试和整理代码。** Codex 可以是架构顾问、执行开发者和代码审查员/导师，但不能代替人的最终判断与真实验证。

```text
选定一个可验收任务 → Codex 阅读相关代码与规则 → 必要时先做 Plan
              → 人确认关键取舍 → Codex 实现与测试
              → 检查 diff + 独立审查 + 人工验收
              → 提交功能分支 → 发 PR → 审核合并 main → 更新任务状态
```

**六条底线：**

1. **先明确完成标准，再生成代码。** 一次只做一个独立、可验收的功能。
2. **仓库是长期事实来源，聊天不是。** 规则、需求、架构、进度和决策落在版本化文档中。
3. **`main` 保持稳定。** 每人使用独立功能分支，借助 PR 集成；尽量避免同时大改同一模块。
4. **完成不等于验证通过。** 检查真实测试命令、输出、接口行为和用户流程。
5. **只授予必要权限。** 密钥、生产数据、部署与破坏性命令要单独保护。
6. **AI 写代码，人必须讲得清楚。** 理解核心调用链、边界条件和技术取舍。

## 1. 哪些工程实践值得现在采用？

| 实践 | 目的 | 小团队建议 |
|---|---|---|
| Harness Engineering | 提供可理解、可验证的工程环境 | **轻量采用** |
| 规格驱动开发（Spec-Driven Development） | 需求、约束、验收先于实现 | **必需** |
| `AGENTS.md` | 固化 Codex 长期规则 | **必需，但简短** |
| Git Feature Branch + Pull Request | 隔离改动、促进审查 | **必需** |
| Testing / CI | 降低回归风险 | **第一周有测试；条件成熟再接 CI** |
| ADR / `DECISIONS.md` | 解释重要架构取舍 | **只记重要决策** |
| TDD | 先写测试，再实现 | **核心复杂逻辑可用，无需全项目强制** |
| Context Compaction | 控制长会话上下文 | **有需要时使用** |
| Skills / MCP | 复用流程、连接外部工具 | **有明确需求再引入** |
| Multi-Agent / Worktree | 并行多任务 | **项目初期不强制** |

不必一次性搭建“企业级流水线”。**能稳定重复执行的简单流程，比堆积工具与规范更有价值。**

## 2. 把项目知识放在仓库，而不是聊天记录里

推荐的最小结构：

```text
project/
├── AGENTS.md             # AI 协作总规则 / 文档索引
├── README.md             # 安装、配置、运行、测试、部署说明
├── docs/
│   ├── PRD.md            # 做什么 / 不做什么（MVP 范围）
│   ├── ARCHITECTURE.md   # 架构、模块边界、数据与接口
│   ├── PLAN.md           # 里程碑及阶段计划
│   ├── TASKS.md          # 可领取、可验收的任务清单
│   └── DECISIONS.md      # 重要技术选型及原因
├── backend/
└── frontend/
```

| 文档 | 回答的问题 | 什么时候更新 |
|---|---|---|
| `AGENTS.md` | Codex 必须遵守什么？ | 长期规则变化时 |
| `PRD.md` | 产品做什么、不做什么？ | 需求或范围变化时 |
| `ARCHITECTURE.md` | 各模块如何组织和通信？ | 实质性架构变化时 |
| `PLAN.md` | 当前处于什么阶段？ | 每周或里程碑结束 |
| `TASKS.md` | 现在谁做什么、怎么验收？ | 任务开始/完成时 |
| `DECISIONS.md` | 为什么这样选型？ | 重要决策时 |
| `README.md` | 新成员如何启动项目？ | 环境、运行和部署方式变化时 |

**划分原则：** 长期原则放 `AGENTS.md`，当前任务放 `TASKS.md` 或当轮对话，重要取舍放 `DECISIONS.md`。不要把日记、整份需求和全部技术细节塞入 `AGENTS.md`；它应是**简短规则 + 文档导航**，让 Codex 按任务读取相关文件。

### 可复用的 `AGENTS.md` 核心模板

```markdown
# 项目协作规则

## 目标
在约定期限内交付可运行、可测试、可维护的 MVP；优先正确性、安全与稳定性。

## 项目文档
- 产品范围：docs/PRD.md
- 系统架构：docs/ARCHITECTURE.md
- 计划与进度：docs/PLAN.md、docs/TASKS.md
- 技术决策：docs/DECISIONS.md
- 使用说明：README.md
只读取当前任务需要的文档，以仓库最新代码及已确认决策为准。

## 技术与设计
- 遵守已确定的技术栈、目录、接口和代码风格。
- 优先简单、可维护的实现，避免无必要的微服务、依赖和抽象。
- 不擅自扩大 MVP 范围；变更重要架构、接口前先解释并取得确认。

## 开发与验证
- 一次只解决一个明确问题，避免无关重构。
- 优先修复根因，关键逻辑补充测试。
- 实际运行验证；未执行的测试不得声称通过。
- 完成后报告改动、测试结果、风险与遗留问题。

## 安全与权限
- 不提交密钥、密码、用户隐私数据或数据库备份。
- 未经明确批准，不推送远程、部署生产、修改生产数据或执行破坏性操作。
- 可自主执行任务范围内的安全本地检查与测试。
- 所有用户数据按身份隔离；API Key 只在服务端保存。
- 数据库访问要校验权限；外部调用处理超时、取消与失败。
- 不得用假数据或静默兜底掩盖真实错误。
```

团队约定：**不需要 Codex 每改一个文件就来申请批准**；要控制的是任务边界、架构变更、生产权限和不可逆操作。

## 3. 一次只交付一个“可验收任务”

“帮我一次完成整个网站”不适合迭代：改动面太大、依赖不清、很难定位错误。每个任务应有**六要素**：

| 要素 | 必须明确的内容 |
|---|---|
| 目标 | 要实现什么对用户可见的行为？ |
| 上下文 | 哪些相关文件、接口、文档和既有约定？ |
| 范围 | 允许修改哪些模块？ |
| 非目标 | 这轮明确不做什么？ |
| 验收标准 | 如何证明正确，包括异常与安全路径？ |
| 完成条件 | 要执行哪些检查、报告什么、何时停止？ |

### 可直接复制的“开发任务提示词”

```text
# 项目：[项目名] / 任务：[任务编号与名称]

目标：[要实现的外部行为、接口或页面]
上下文：[相关需求、架构文档、代码路径、已有协议]
修改范围：[本轮允许修改的模块]
非目标：[不实现的相关功能；不进行无关重构]

工作方式：
1. 先读取 AGENTS.md 与本任务有关的文档、代码，确认当前实现。
2. 如需修改既定架构、API 协议或新增重要依赖，先说明理由与取舍。
3. 在任务范围内自行实现、执行测试、修复失败；优先最简单可维护方案。
4. 不扩展任务范围，不用 Mock/假数据掩盖真实运行错误。

验收标准：
- [正常路径]
- [异常路径、权限、安全与边界情况]
- [测试/运行命令及期望结果]

结束时报告：
- 修改了哪些文件、为什么；
- 核心实现方式；
- 实际执行的命令、真实结果、未执行的验证；
- 遗留问题、风险与是否达到验收标准。

完成当前任务后停止；未经明确批准，不提交、推送或部署。
```

**具体例子：登录 API。** 目标为 `POST /api/v1/auth/login`，邮箱密码校验成功后签发有有效期的身份凭证。验收不能只看“成功登录”，还必须覆盖**错误密码、用户不存在、密码不明文保存、凭证有效期、错误响应不泄露凭据、关键路径自动化测试**。本轮**不做**注册、密码找回、第三方登录、管理员功能。

### 什么时候先让 Codex 做 Plan？

| 任务复杂度 | 做法 |
|---|---|
| 按钮文案、简单健康检查接口 | 直接实现 + 验证 |
| 数据库认证、前后端协议变更 | **建议先 Plan** |
| AI 多轮辩论状态机 | **强烈建议先 Plan** |
| 整体架构重构、数据库迁移、生产部署 | **必须先审查方案与风险** |

Plan 用于**复杂、高风险、跨模块任务的方案对齐**，不是每次改一行代码都必须进行的仪式。方案确认后，允许 Codex 完成本轮安全范围内的多个步骤。

## 4. Git + PR：两个人如何不互相覆盖代码？

**基本规则：每人自己的功能分支，`main` 始终尽量可运行；通过 PR 合并经过验收的代码。** 不共享一个无边界的大 Codex 会话，也不让两个 Codex 同时大范围改同一批文件。

```text
main（稳定、可运行）
├── feat/auth           开发者 A + Codex：后端认证
└── feat/topic-page     开发者 B + Codex：前端辩题页面
           ↓ 功能测试 + diff 审查 + PR
       合并到 main
```

### 从领取任务到发 PR 的最小 Git 流程

以下假设工作区**没有未提交改动**、远程名为 `origin`、主分支为 `main`：

```bash
# 1. 同步并切回主分支
 git switch main
 git pull --ff-only origin main

# 2. 为本任务开分支（不要长时间直接写 main）
 git switch -c feat/health-check

# 3. 开发过程中查看改动
 git status -sb
 git diff --stat
 git diff

# 4. 在 backend 目录做真实验证
 cd backend
 go test ./...
 go vet ./...
 cd ..

# 5. 检查 diff 和暂存区，再提交
 git diff --check
 git add backend/
 git diff --cached --stat
 git diff --cached
 git status -sb
 git commit -m "feat: add backend health check"

# 6. 推送功能分支，在 GitHub 创建 PR
 git push -u origin feat/health-check
```

**审查命令关键区别：** `git status -sb` 看到新文件和工作区状态；`git diff` 看**未暂存的已追踪文件改动**，默认不展示新建未追踪文件；`git diff --cached` 看**已暂存、即将提交**的改动；`git diff --check` 查空白错误。审查 PR 时，可先 `git fetch origin`，再运行 `git diff origin/main...HEAD` 查看相对主分支的变更。

**提交前检查**：`.env`、真实 API Key、数据库备份、用户资料不在暂存区；不要未检查就 `git add .`。`.gitignore` 只能防止 Git 默认追踪，**不能阻止有权限的程序读取文件**，也不会自动移除已被追踪的秘密。

**PR 合并前**：描述任务和修改范围、测试证据、截图/接口样例（若适用）、风险；由另一位队员审查，修改通过后合并。条件允许可加分支保护与 CI；没有 CI 时必须手工跑检查。功能合并后，同步最新 `main` 再开启下一个任务。

**暂时不必强制学习 Git Worktree。** 两人各自电脑 + 功能分支已足够；以后一个人同时开多个 Codex 会话、需要在同一仓库并行检出不同分支时再用 Worktree。

## 5. “Codex 说测试通过”不等于真实验收

**四层验收不能混为一谈：**

| 层次 | 典型验证 | 核心问题 |
|---|---|---|
| ① 静态检查 | `go vet ./...`、TypeScript 类型检查 | 是否有基础编译/静态问题？ |
| ② 自动化测试 | `go test ./...`、关键业务用例 | 正常、异常及边界逻辑是否正确？ |
| ③ 集成验证 | 真实 HTTP 请求 + 测试 MySQL + 第三方调用 | 各模块是否真正连通？ |
| ④ 手工验收 | 浏览器完整操作核心流程 | 用户是否真的能用？ |

还要考虑**旧功能是否回归**：如登录的错误密码、跨用户访问、过期凭证、数据库异常；AI 辩论的模型超时、用户连续点击、轮次状态、重复请求与取消。

AI 输出还要单独做**质量评估**。可固定 **10 个测试辩论场景**，检查：是否坚持指定立场、是否记住历史论点、是否按轮次结束、总结是否基于真实发言。不要在缺乏数据时声称“准确率 95%”。

### 可直接复制的“只读代码审查提示词”

```text
请严格审查当前功能分支相对于 main 的改动。
本轮只审查，不修改文件，也不提交、推送或部署。

重点检查：
1. 是否满足任务的全部验收标准；
2. 是否存在真实业务逻辑错误；
3. 是否破坏现有 API、数据库行为或兼容性；
4. 是否存在越权、敏感数据泄露或不安全输入；
5. 是否遗漏超时、取消、错误处理和边界条件；
6. 是否存在无必要的抽象、复杂设计、额外依赖或无关修改；
7. 测试是否覆盖重点、能否实际运行。

输出时：
- 按严重程度列出问题、涉及文件及具体位置；
- 区分“已确认问题”与“潜在风险”，不要凑数；
- 说明实际执行了哪些验证、哪些未执行；
- 给出是否建议合并 main 的结论；
- 若不能合并，列出最小必修复项。
```

**实现和审查应分为两种任务视角。** Codex 写完后，先审查、再修复；人的最终验收不能外包给 AI。

## 6. 用 AI Coding 的同时真正学会开发

**不要追求逐行手敲全部代码；要沿业务调用链理解核心逻辑。** 例如一个 AI 辩论请求：

```text
Vue 点击发送 → HTTP 请求 → Gin Router → Handler 校验输入/身份
→ Service 校验会话与轮次 → Repository 读取历史消息
→ Eino 调用大模型 → 保存 AI 回复 → 返回前端展示
```

| 代码类型 | 建议掌握深度 |
|---|---|
| 普通 Vue 样式、布局 | 能读懂、能修改 |
| Gin 路由、HTTP JSON、GORM/数据库访问 | 理解原理、能独立排错 |
| Eino 调用、辩论会话状态、身份权限控制 | 深入理解，能向队友/面试官讲清设计 |

**学习每个核心功能时问 Codex：**“它在哪一层、为什么放这里、有没有更简单的方案？数据库异常、模型超时、请求重复或用户连续点击时会怎样？” 然后**自己做一次小修改**，例如把三轮辩论改为四轮，验证轮次规则是否清晰。业务约束不能只依赖提示词：重要状态/权限必须在服务端验证。

## 7. 七类高频陷阱与权限边界

| 风险 | 典型表现 | 正确做法 |
|---|---|---|
| 过度设计 | 小功能引入许多接口/分层 | 逐个解释抽象必要性，优先最小方案 |
| 幻觉式完成 | 自称成功但没运行 | 索要真实命令、结果、证据 |
| 无关修改 | 修登录时顺手重构全部后端 | 限制范围、检查 `diff` |
| 上下文过时 | 沿用已废弃选型或方案 | 当前仓库代码与确认后的文档优先 |
| 修补式编程 | 用特殊判断不断掩盖 Bug | 查根因，加回归测试 |
| 依赖污染 | 为小功能加入很多包 | 每个新依赖都说明必要性 |
| 不安全操作 | 泄密、删库、擅自部署 | 最小权限，高风险人工审批 |

**三项不可忽略：**

- **本地可读不代表安全**：`.gitignore` 并非隔离机制；尽量不要把生产密钥放在日常 AI 编码工作区。
- **本地验证与生产操作分开**：可允许本地构建、测试、开发服务；生产 SSH、删除数据、迁移、远程推送、部署等需要人明确批准。注意真正需要的权限取决于 Codex 当前工具与沙箱配置。
- **依赖/API 以实际版本为准**：尤其 Eino 等持续更新的框架，核对官方示例、已安装版本和可编译 API，不为“追新”牺牲稳定性。

## 8. 双人/多人协作：先约定接口，再并行实现

适合「思弈阁 Lite」的示范职责（可随团队能力调整）：

| 成员 | 主要负责 | 应共同检查的部分 |
|---|---|---|
| A + Codex | Go/Gin API、MySQL、Eino、身份认证、会话状态、服务器部署 | 鉴权、接口协议、状态规则、端到端联调 |
| B + Codex | Vue3/TypeScript 页面、辩题选择、聊天 UI、历史记录、前端测试 | 请求/响应结构、错误处理、用户体验 |
| 全队 | 需求范围、接口契约、PR 审查、联调和演示 | 每个关键功能的真实验收 |

前后端并行前，写清 **HTTP 方法 + 路径 + 请求/响应 JSON + 错误码 + 身份要求**。例如，以下是**仅供讨论的接口草案，不是已经确认的协议**：

```http
GET  /api/v1/topics
POST /api/v1/debates
POST /api/v1/debates/{id}/messages
GET  /api/v1/debates/{id}/messages
```

前端可先依照**双方确认的接口结构**开发；Mock 只能用于未接通时的开发和测试，联调验收必须切换到真实后端，不可用假数据冒充成功。前端同学也需要理解 HTTP、Vue 组件与接口输入输出。

**协作约定：**小 PR、明确任务归属；接口/数据模型一旦变更先沟通；跨模块验收双方参加；`DECISIONS.md` 记录类似“为何从 go-zero 改 Gin”的技术理由。

## 9. Context、Skills、MCP 与多 Agent：按需升级

- **Context Compaction（上下文压缩）**：一个功能结束就可开新 Codex 会话，避免旧尝试、过期建议污染当前任务。重要信息先写回 `TASKS.md` / `DECISIONS.md`；压缩不能替代仓库文档。
- **新会话起手式**：`请阅读 AGENTS.md 和本任务相关文档，检查当前代码状态，只完成 TASK-08，执行验证并报告结果。`
- **Skills**：当同一流程稳定重复 3～4 次（例如接口完成后跑测试、检查 API、生成 PR 摘要），再考虑封装；避免创建大量没有明确用途的 Skill。
- **MCP**：确实需要连接特定外部服务时才接；权限按需授予。
- **Multi-Agent / Worktree**：待任务边界独立、测试成熟、并行冲突成本可控后再学习，不是初期前置条件。

**原则：聊天是临时工作记忆，版本化的代码、文档与测试才是项目的长期依据。**

## 10. 每日节奏与从零启动

### 每日“五步闭环”

- [ ] **开始前**：看 `TASKS.md`，领取一个明确任务，确认验收条件与分支归属。
- [ ] **任务开始**：Codex 查看相关代码；复杂任务先 Plan，必要的技术取舍由人确认。
- [ ] **实现结束**：执行真实测试、检查文件变更、理解关键实现。
- [ ] **验收时**：做只读审查与实际操作，修复关键问题、补回归测试。
- [ ] **任务完成**：提交并推送功能分支，创建/审查 PR，合并后更新任务状态和重要决策。

无须每天重讲整个项目、重写长日志；记录**任务状态、关键决策、验收证据**就够了。

### 新项目（以一个月的思弈阁 Lite MVP 为例）

1. **Phase 0：明确范围与规则。** 从申报书收敛出 MVP、`AGENTS.md`、`PRD.md`、`ARCHITECTURE.md`、`PLAN.md`、`TASKS.md` 和 `DECISIONS.md`，人工审核技术栈与边界；不要让 Codex 无审查地把申报书直接变成大量代码。
2. **审查架构**：确认 Gin + Eino + MySQL、单体后端、Vue3 + TypeScript + Arco Design、AI 多轮辩论状态、关键数据结构、用户鉴权与接口契约。需要改变原申报书选型时，在决策文档写明理由。
3. **第一周：最小可运行骨架。** 建前后端、健康检查接口、README；保证双方本机能启动、测试通过；尽早建立可访问的**测试环境**，密钥与生产数据单独管理。
4. **第二周：按模块并行。** A 做后端、B 做前端；确认 API 契约后分别领取任务，逐个完成 PR 与联调。
5. **第三周及后续：加强回归/CI 与闭环。** 加入完整数据库、真实大模型调用、固定场景评估和关键用户流程；条件成熟后接自动 CI，持续修复问题、准备演示。

**交付优先级：能启动 → 能完成一条真实核心流程 → 可验证、稳定 → 可部署、可解释。** 不为了功能数量和技术新颖度牺牲可演示性。

## 12. 最重要的三个结论

1. **明确的验收标准比超长提示词重要。** Codex 必须知道做到什么程度才算完成。
2. **Git + 测试 + PR 是 AI Coding 的安全网。** 生成快不是质量保证；代码必须能验证、回退和解释。
3. **掌握的是工程判断，不只是代码阅读。** 理解业务数据流、模块边界、技术取舍、故障与安全，才能真正与 Codex 协作。
