# V2-04 原文批注引用生成改造方案

2026-11-19 · 待评审 · 适用范围为现有四轮基础练习。本文记录第三场已观测的故障，并给出局部改造及验收方案。原文锚点和逐轮批次以 [V2-04 锚点设计](V2_04_ANNOTATION_ANCHOR_DESIGN.md) 为基础，产品要求见 [PRD §5](../product/PRD.md#5-特色一原文批注与局部重练) 和 AC-V2-13～16。

## 1. 故障证据

| 隔离 Demo 会话 3 | 正式发言 | 批注适配器与账本 | 批注业务层 |
| --- | --- | --- | --- |
| 第 1 轮，轮次记录 9 | 已提交 | 第 2 笔调用结算为 `success`，输入 1,702、输出 513 Token | `failed / model_error`，日志 `anchor_not_located` |
| 第 2 轮，轮次记录 10 | 已提交 | 第 4 笔调用结算为 `success`，输入 2,934、输出 499 Token | `failed / model_error`，日志 `anchor_not_located` |

只读核查时，会话完成 2/4 轮，账本有 4 笔预留。两笔批注均通过适配器的 JSON 解析和字段校验。服务端能在本次白名单中找到模型选择的消息，但至少一条候选引用在该消息中无法逐字定位。`toAnnotationItems` 遇到首条无法定位的引用就返回错误，`generateAnnotation` 随后将整个批次标记为失败。

现有日志没有保存模型原始回复，无法区分模型改写原句、标点差异和选错白名单内的消息，也无法知道被整批丢弃的内容里有多少条有效候选。第三场当时尚未生成复盘，本次证据无法评价复盘提示词的修复效果。第二场第 2 轮也曾在适配器成功之后被业务层拒绝，其具体子原因未留下证据。 [批注适配器](../../backend/internal/ai/annotation_adapter.go) · [业务转换与保存](../../backend/internal/debate/annotation.go) · [原文定位规则](../../backend/internal/debate/anchor.go) · [试用记录](V2_04_ANNOTATION_SELF_TEST.md)

## 2. 设计决策

**局部重构模型与批注服务之间的引用协议。** 服务端提前从已提交发言生成可选片段。模型从给定编号中选择证据，并撰写理由和改进方向。服务端再从该编号映射回正式消息、准确坐标和逐字原文。

| 做法 | 判断 |
| --- | --- |
| 加强逐字引用提示词 | 当前提示词已要求精确复制且禁止修改标点，仍出现两轮连续失败。可以完善编号选择说明，重复强调逐字复制的收益有限。 |
| 使用供应商 JSON 模式 | 可以约束 JSON 格式。本次两个批次已通过格式校验，JSON 模式无法核对某段引用是否属于指定原文。 |
| 用近似匹配纠正原句 | 同一句可能在双方发言或多个轮次出现。近似匹配容易把有说服力的解释挂到错误证据上，增加错标风险。 |
| 服务端预分片，模型选择编号 | 编号直接映射到服务端原始区间，能消除模型抄写和计数误差。需要验证分片粒度、编号选择质量和额外输入成本。采用这一方案。 |

借鉴 Claude API 对预定义文本块的索引引用。思弈阁保留当前供应商，通过普通 JSON 返回编号，继续沿用现有消息 ID、精确原句和 Unicode 位置。定位准确只代表引用可回查，批注理由是否成立仍需看内容。 [Claude 预分块引用](https://platform.claude.com/docs/en/build-with-claude/citations) · [W3C 文本位置选择器](https://www.w3.org/TR/annotation-model/#text-position-selector) · [DeepSeek JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)

### 本次改动边界

- 修改批注输入编排、内部 JSON 输出、逐条校验及脱敏日志。把现有 `annotation-v1` 的提示词追溯标识升为 `annotation-v2`，便于区分两种生成方式。
- 继续按轮次生成，每轮合计 0–3 条。复用现有所有权校验、单分析槽、`attempt_version`、租约、手动重试规则、费用账本和正式发言的提交路径。
- 批注引用改造沿用现有 HTTP 响应和数据库格式。试用模式的补做按钮单列为界面能力修正，见 §6。
- 教练视角、批注分类、完整论证树、复盘生成和四维战报留给各自需求。实现和真实模型复验分别按现行授权执行。

## 3. 片段和内部输出契约

```text
已提交的消息 → 服务端片段目录 → 模型选择编号并给出训练反馈
            → 服务端逐条复核 → 按现有锚点格式保存有效批注
```

### 3.1 片段生成

1. 在现有批次认领后，使用 `AnnotationClaim.Sources`。只读取本会话、触发轮及以前已提交的正式消息，按轮次及原有消息顺序处理。
2. 每个可选片段属于一条消息。优先在换行或中英文句末标点处切分，保留标点和 Markdown 原始字符。按已提交原文计算 Unicode 码点半开区间 `[start_cp, end_cp)`。纯空白片段无需编号，引用仍按原始区间取值。
3. 以约 120 码点为首版粒度目标，适当合并连续短片段。每个可选片段最多沿用现有引用上限 300 码点。超长句优先在逗号、分号或空白边界细切。遇到没有安全切点的超长文本，保留为可阅读的上下文并统计不可选片段，避免在组合字符或 emoji 中间制造锚点。具体粒度通过离线样例校准。
4. 为每个可选片段分配请求内唯一的短编号，如 `f01`。同一句出现在不同位置或不同发言中，会拿到不同编号。映射只在本次尝试中使用，编号不能跨尝试或跨会话解释。
5. 每条消息的提示词提供轮次、发言者以及当前轮或历史上下文标记。用序列化分隔元数据与原文，沿用现有请求消息数和顺序。原文在对应片段或上下文中呈现一次，避免同时发送全文和副本。历史发言仍可用作与本轮有关的证据。新增发言是本轮评价主对象，历史引用是否真正相关由质量评测检查。
6. 服务端验证区间有序、非空且未越界，保存前继续用原文复核。自定义辩题标题、背景及发言仍按不可信数据处理。题目、提示词和分隔符不得出现在可引用片段表中。片段表在进程内建立，正文里的伪造编号或 JSON 不得改变该表。

示意映射使用消息 `101` 的原文「先定义标准。再比较结果。」。

| 编号 | 消息 | 起止码点 | 原文 |
| --- | --- | --- | --- |
| `f01` | `101` | `[0, 6)` | 先定义标准。 |
| `f02` | `101` | `[6, 12)` | 再比较结果。 |

这里把两句分开用于说明映射，工程实现可以按粒度规则合并相邻短句。颜色、线型、点击定位均读取原有锚点字段。

### 3.2 模型只返回候选

```json
{
  "items": [
    {
      "fragment_id": "f01",
      "category": "strength",
      "label": "标准清楚",
      "reason": "先给出标准，让后续比较有共同依据。",
      "improvement": "补一句这个标准适用的范围。"
    }
  ]
}
```

- 根对象仍只有 `items`。校验 UTF-8、总字节上限 16 KiB、唯一键和 0–3 条上限。每条候选必须含上述五项。沿用四类枚举以及标签 40、理由和改进方向各 300 码点的约束。
- 模型输出只认请求内的 `fragment_id`。服务端从片段表取消息和区间，从正式原文取 `quote`，从消息元数据取 `turn_no` 和 `role`。保存和 API 仍输出 `anchor.message_id`、`quote`、`start_cp`、`end_cp` 和 `resolved`。前端继续复核字素边界，原有待核对降级照常工作。
- 一条候选只能绑定一个连续片段。V2-06、V2-07 的多方回应关系可复用最终锚点，超出本次内部契约。

## 4. 逐条校验和批次结果

批次级检查先于逐条检查。根对象无效、`items` 不是数组、条数超限、输出超限或供应商响应不可用时，直接按现有错误路径结束。根对象有效时，按原顺序处理候选。

| 输入情形 | 批次结果 | 诊断 |
| --- | --- | --- |
| 模型明确返回 `{"items":[]}` | `completed`，保存空数组 | `ok`，候选数为 0 |
| 候选全部通过 | `completed`，保存全部有效条目 | `ok` |
| 至少一条有效，其他条目编号不存在、字段无效或与已接受条目完全重复 | `completed`，保存有效条目 | `partial_items_rejected`，记录各类丢弃计数 |
| 模型给出候选，但一条也无法通过 | `failed / model_error` | `all_candidates_rejected`，记录各类丢弃计数 |
| 服务端权威片段表损坏、授权消息或原文复核出现内部不一致 | `failed`，整批不保存 | 按内部失败分类记录，禁止尝试挂到其他消息 |
| 原子保存失败 | 沿用既有存储失败语义 | `store_failed` |

同一片段可有不同类别或理由的批注。完全重复保留第一条。一次尝试只写一个批次结果，旧版本的慢回复仍不能覆盖新版本。正式发言、总结或其他轮次不受该批次失败影响。

日志沿用 `error_code`、`reason_code` 和轮次定位信息，增加 `prompt_version`、候选数、接受数和固定类别的丢弃计数。按标签或候选编号自由拼接日志会引入不可信内容，因此只记录固定字段与数值。原文、模型回复、模型生成的编号及理由不入日志。所有候选无效和模型返回零条需能从日志与存储状态分别识别。

## 6. 历史、补做和费用

- **历史兼容。** 加载已经落库的批注时仍使用旧锚点格式和原有精确回读规则。能精确定位的继续显示，旧有歧义仍可显示待核对。无需补写片段编号或重新计算历史批注。已有失败记录保留，发布后由已有受控手动入口处理符合资格的失败批次。
- **补做能力。** 受控真实试用明确禁止手动补做，页面目前仍可能显示按钮。优先复用服务端已提供的能力信号；如果没有，可单独评审给批注列表添加可选布尔值 `manual_retry_enabled`。明确为 `false` 时去掉按钮，显示「本次测试未开放手动补做」。字段缺失沿用旧行为，允许补做时仍按现有批次状态控制。采用这一字段时同步 API、OpenAPI、客户端和兼容测试；批注引用改造可独立交付。
- **费用和延迟。** 每个批次继续最多发起一次真实请求。原有超时、Gate、分析槽及账本保持生效。当前 Demo 按请求的实际 JSON 字节数加 1,024 计算输入预留，单次上限为 50,000，单次输出上限为 4,096。用常见四轮内容、临界长度及最大合法输入分别核对新版与原版请求体积，并验证本地处理时间。八条发言都达到 2,000 码点且大量使用四字节字符时，原文本身就可能超过试用的单次预留。对于超限场景，先减少编号和分隔开销并保留正式发言上下文。仍超限时沿用出网前拒绝，记录预算分类；实际生成速度另由获准的真实复验观察。费用或调用范围的改动另行确认。

## 7. 验收清单

### 离线验收

| 场景 | 通过条件 |
| --- | --- |
| 两边引用同一句、同一消息重复、不同轮复述 | 每个位置编号不同，已保存的消息 ID 与坐标和所选片段一致。 |
| 中文标点、Markdown、引号转义、CRLF、emoji、组合字符、长句 | `quote` 等于正式原文的精确切片。坐标不切坏可见字素，无法安全标出的内容遵守降级规则。 |
| 原文出现伪造编号或伪造 JSON | 用户原文仍是数据，未改变服务端目录。未来轮和其他会话的原文无法进入或被选中。 |
| 三条候选有一条无效或完全重复 | 两条有效结果可通过原 API 返回和双向定位，日志记录一条丢弃。 |
| 零条、全部无效、非法根结构、超出三条 | 按 §4 分别处理，全部坏的批次不会显示为正常零条。 |
| 超时、槽位忙、回调重复、旧版本返回、晚到的最终轮批注 | 沿用现有状态和认领规则。正式发言与复盘继续推进，没有重复调用或旧版本覆盖。 |
| 旧数据和刷新 | 历史批注仍可定位，开关和展开行为通过现有浏览器用例，无迁移和补跑。 |
| 四轮常见、临界和最大输入 | 能容纳的样例继续发起至多一次请求，超限样例在出网前被拒绝。报告与旧版的实际字节差和受影响边界，预算保持不变。 |

后端先运行相关单测，再执行 `go test ./internal/ai ./internal/debate ./cmd/server`、对应的 `go vet` 和构建。若涉及批次并发或写回，补跑相关竞态用例。涉及补做入口时运行前端类型检查、相关 Vitest、构建和 Mock 浏览器回归。只有另获隔离库写入授权后才运行需要写库的集成测试。

### 单独授权的真实复验

用独立预算窗口和一场完整基础模式，逐轮记录正式发言、批注状态、候选数、接受数、丢弃原因、延迟与调用账本。核对以下结果后再申请负责人签收。

- 四轮正式发言和赛后复盘有独立、可回查的结果。
- 可见批注全部能在正确发言中回查原文。复验中人工抽查解释是否贴合原句、改进方向是否可执行，并检查是否出现大片段引用导致的指向不清。
- 无有效原文的条目均未显示。若有部分拒绝，已确认有效条目仍保存；若有整轮失败，保留原因码和账本证据再判断下一步。
- 不依赖额外补做使测试通过。显式空批次可以成立，但若整场都没有可供抽查的批注，只能确认流程运行，批注质量仍待验。

### 交付判断

预计为 **中等规模的后端切片**。主要风险是片段过粗使反馈指向不清、片段过细增加提示词开销，以及模型选择了真实但不相关的片段。通过离线预算验证和实际内容抽查分别确认。失败可回退应用版本，历史批注随现有锚点格式继续读取；回退保留已写入数据和账本，任何额外模型调用另行授权。
