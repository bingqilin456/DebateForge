## 3. 已确认与草案的分界

| 项 | 结论 | 归因 |
| --- | --- | --- |
| 计费模式 | 用户填写自己的 API Key，模型调用费用由用户承担 | `[已确认]` 用户本轮明确答复（SUP-01） |
| 平台代付 | 不支持平台兜底代付 | `[已确认]` 由上述答复直接否定（SUP-01） |
| 维护者公用密钥页 | 不作为本版必需的配置页面 | `[已确认]` 由上述答复直接否定（SUP-01） |
| 配置方式 | 通过界面配置四项字段，不要求用户编辑文件或环境变量 | `[补充草案]` 由"界面配置"方向展开，未逐条确认（SUP-02） |
| 四项字段组成 | 服务商、API 地址、模型、API Key | `[补充草案]` 本轮提案，待负责人审阅（SUP-02） |
| Key 服务端隔离与脱敏 | 服务端按用户隔离保管；浏览器只负责输入与提交，只显示受控脱敏摘要 | `[补充草案]` 沿用仓库既有安全约束（秘密不入库明文、不回显、按用户隔离），非用户逐字确认（SUP-03） |
| 保存与测试分离 | 两个独立状态、两个独立操作；测试须用户主动触发并提示可能收费 | `[补充草案]` 本轮提案，待审阅（SUP-04） |
| 替换或移除只影响后续 | 不改写历史、复盘、批注、争点卡与重练版本 | `[补充草案]` 本轮提案，待审阅（SUP-05） |
| 无配置阻止范围 | 阻止新的正式生成调用，不阻止读历史 | `[补充草案]` 本轮提案，待审阅（SUP-06） |

- `[补充草案]` 上表**只有前三行**是用户明确答复；其余六行是据此方向提出的补充草案，未经逐条确认、未签收。它**不是** Q53，也不改写 Q1–Q52 的任何结论。
- `[已确认]` 归因纪律以 [PRD §19](../PRD.md#19-v2-需求补充用户自带模型服务2026-11-17草案待确认) 开头两段为准；本表不扩大用户答复的范围。
- `[已确认]` 供应商真实余额无法直接查询时**不得虚构**：界面只能展示本应用侧可观测的计数与状态，见 §6。

## 4. 页面结构与字段

`[补充草案]` 版面组织如下（线框只表达控件与顺序，不追求像素级一致）：

```
┌ 设置 · 模型服务 ────────────────────────────────────────────┐
│ 配置状态：未配置 / 已配置（受控脱敏摘要） / 校验失败          │
│ 服务商   [ 选择：……                                     ▾ ] │
│ API 地址 [ https://……                                      ] │
│ 模型     [ ……                                              ] │
│ API Key  [ ••••••••••••••  （输入后不可再读回）            ] │
│           Key 只提交到服务端隔离保管，本页不再显示完整内容   │
│ [保存]   [测试连接（可能产生一次真实调用与费用）]             │
│ 保存状态：未保存 / 保存中 / 已保存 / 保存失败（受控错误）     │
│ 测试状态：未测试 / 测试中 / 成功 / 失败（受控错误，不含原文） │
│ 提示一：测试连接只由你主动触发，不会自动执行或自动重试        │
│ 提示二：替换或移除配置只影响后续调用，不改写已保存的历史      │
└────────────────────────────────────────────────────────────┘
```

| 字段／控件 | 约束 | 展示方式 |
| --- | --- | --- |
| 配置状态 | 只读汇总，由服务端配置存在性与最近一次结果决定 | 文本徽标：未配置／已配置（掩码）／校验失败 `[设计建议]` |
| 服务商 | 选择项；首版支持集合属 TE-16，未定 | 下拉选择；不支持时给受控提示 `[设计建议]` |
| API 地址 | 必填；协议、内网地址与重定向校验属 TE-15，未定 | 单行文本，等宽显示 `[设计建议]` |
| 模型 | 必填；随服务商而定的可选集合属 TE-16，未定 | 单行文本 `[设计建议]` |
| API Key | 只提交、不回显、不落明文；长度与字符集校验属技术方案 | 密码型输入，提交成功后清空；已配置时只显示服务端生成的固定掩码或"已配置" `[设计建议]` |
| 保存 | 独立操作，不与测试合并 | 主按钮 `[设计建议]` |
| 测试连接 | 独立操作，可能真实计费；准入是"存在完整候选配置"而非"曾测试成功" | 次按钮，标注可能产生费用 `[设计建议]` |
| 保存状态行 | 未保存／保存中／已保存／保存失败，失败给受控错误并保留已填内容 | 文本行，忙时禁按钮 `[设计建议]` |
| 测试状态行 | 未测试／测试中／成功／失败，失败给受控分类 | 文本行，与保存状态互不回写 `[设计建议]` |

`[设计建议]` 控件层的可用条件与不可用表现：

| 操作 | 可用条件 | 不可用时的表现 |
| --- | --- | --- |
| 保存 | 四项字段通过本地必填与格式校验 | 按钮禁用，说明缺哪一项或哪项格式不合法 `[设计建议]` |
| 测试连接 | 存在一份完整候选配置（"完整"的口径属 TE-18，见 §7） | 按钮禁用并说明还缺什么；不因"未测试""上次失败"而禁用 `[补充草案]` |
| 移除配置 | 当前存在已保存配置 | 无配置时不显示该操作，避免误解为可撤销不存在的值 `[设计建议]` |
| 替换配置 | 当前存在已保存配置、用户重新填全四项并保存 | 只填部分字段时按"修改未保存"处理，不视为替换 `[设计建议]` |

- `[设计建议]` 已配置时只显示**受控脱敏摘要**（例如"已配置"或由服务端生成的固定掩码），**不渲染 Key 的任何明文片段**（含首尾若干位之类的切片）；输入框在提交后清空；保存后无法再取回完整 Key（AC-V2-33）。
- `[设计建议]` 正常页面的脱敏摘要与错误路径要分开看：错误提示、日志一律不出现任何片段；演示图中的 `••••••••` 只是格式占位，不出现任何完整形态的 Key。
- `[设计建议]` 保存与测试不能合并成一个"保存并测试"按钮；测试结果不回写为保存结果，保存也不触发测试。
- `[待决]` 测试针对的是"当前完整候选配置"还是"已保存配置"，以及二者的版本一致性，PRD §19.3 未定；定稿前不假定两者相同，也不据此写死按钮文案。
- `[补充草案]` 是否需要"名称／备注"以支持多配置，随多配置议题一并待决（§7）。

## 5. 状态与操作

| 状态／操作 | 触发 | 表现 | 禁止 |
| --- | --- | --- | --- |
| 未配置 | 首次进入、移除后 | 说明"配置后才能发起新的模型调用；历史仍可查看"，给"去设置"或填写入口 | 阻止读历史、把未配置显示为错误 |
| 已保存·未测试 | 保存成功但未测试 | 明确"已保存、尚未测试" | 把"未测试"显示为失败或不可用 |
| 已保存·上次测试失败 | 测试返回失败 | 显示最近一次失败的受控分类与"可再次手动测试" | 因上次失败而禁止再次手动测试 |
| 已保存·测试成功 | 用户显式测试成功 | "连接可用（本次测试可能已计费）" | 宣称可查供应商余额、硬保证费用上限 |
| 保存中 | 用户点击保存 | 忙碌态，保存与测试按钮禁用 | 重复提交、自动重试 |
| 保存失败 | 校验失败或服务端错误 | 受控错误；保留已填内容，允许修改后重试 | 显示 Key 或上游原文、请求头 |
| 测试中 | 用户主动点击测试 | 加载态，测试按钮禁用，不改保存状态 | 自动重试、后台静默重测 |
| 测试失败 | 超时、鉴权、额度、协议错误 | 受控分类提示＋"可再次手动测试" | 自动换模型或换地址重试、显示上游原文 |
| 替换配置 | 用户重新填写并保存 | 只影响后续调用；历史、复盘、批注、重练版本不变 | 追溯改写历史结果 |
| 移除配置 | 二次确认 | 后续生成调用被阻止，历史仍可读 | 删除历史、删除复盘或批注 |
| 修改未保存 | 用户在表单中改动 | 提示"有未保存的修改"（与共通态一致） | 静默丢弃已填内容、离开时不提醒 |

- `[补充草案]` **测试的准入条件不是"以前测过且成功"**：只要表单构成一份完整候选配置，用户就可以显式发起测试；未测试或上次测试失败**都不构成**禁止再次手动测试的理由，否则会形成"必须先测试成功才能测试"的循环。缺字段时按钮禁用并说明缺哪一项。
- `[补充草案]` 测试可能真实计费，**只由用户主动触发**：不自动测试、不自动重试、不在保存时隐式测试；页面须明确提示这一点（AC-V2-35）。
- `[补充草案]` 错误提示**不含 Key 或其任何片段**、**不含上游原始响应与请求头**；跨用户不可见或读不到他人配置（表现为不可见／404 语义，AC-V2-34）。其中"不回传供应商原始响应"沿用仓库既有安全约束。
- `[补充草案]` 替换或移除配置**只影响后续调用**：已保存的历史、复盘、批注、争点卡与重练版本内容不变、仍可读取，不追溯改写（AC-V2-38）。
- `[已确认]`（继承既有约束）并发与额度限制与 Key 无关地独立生效；界面须区分"配置问题""应用额度／并发问题"与"供应商侧错误"，不混成一句"服务不可用"。
- `[设计建议]` 工作台等入口在无配置时给一次性说明与"去设置"入口，不反复弹窗打断；去向见 [开始练习](02-entry.md)。
- `[待决]` 生成进行中替换或删除配置时，在途调用继续用旧值还是拒绝，属 TE-17，本表不预设结论；未定前按"只影响后续"描述，不承诺在途行为。

`[设计建议]` 失败分类按下面拆开，同一分类同时用于保存失败与测试失败的状态行；只给受控分类与恢复动作，不暴露上游细节：

| 分类 | 典型原因 | 界面表现 | 恢复动作 | 禁止 |
| --- | --- | --- | --- | --- |
| 表单不完整 | 四项字段缺任意一项、格式明显非法 | 指出缺哪一项，按钮禁用 | 补全后重新保存或测试 | 用"服务不可用"概括 |
| 鉴权失败 | Key 无效、过期或权限不足 | "服务商拒绝鉴权，请检查 Key 是否有效" | 重新填写并保存后可再次手动测试 | 提示 Key 的具体内容或哪一段不合法 |
| 地址或协议不可达 | 地址错误、超时、协议不兼容、目标被拒 | "无法连接该地址"或"该服务商协议暂不支持" | 改地址或换服务商后重试 | 显示 DNS、内网地址、上游状态码全文与请求头 |
| 应用额度或并发受限 | 每日生成次数用尽、单用户或全局并发已满 | 明确是应用侧限制、何时可再试 | 等额度恢复或等并发释放 | 与配置问题混成一句、暗示 Key 无效 |
| 供应商侧错误 | 供应商限流、供应商侧额度不足 | "服务商侧返回错误，费用与余额请以服务商为准" | 稍后手动重试或更换服务商 | 伪造供应商余额、替用户判断可充值额度 |

- `[补充草案]` 上表五类不得合并成一句"服务不可用"；其中"应用额度或并发受限"与 Key 是否有效无关，界面必须说明这一点，避免用户误以为要重新填 Key。
- `[设计建议]` 失败信息只出现在状态行与受控提示区域，不写进配置文件、不写进日志正文；技术评估对 SSRF 与协议适配的规则属 TE-15、TE-16，本文不写校验细节。

## 6. 额度边界（P11）

- `[补充草案]` 自带 Key 的**供应商侧费用**与**应用侧次数／并发额度**是两套约束，界面须分开说明；应用仍按既有额度控制（每用户每日生成尝试上限、单用户并发 1、全局并发 2 等），不因用户自带 Key 而取消或改变（SUP-07 边界约束，由 SUP-01 推出，非用户逐条确认）。
- `[补充草案]` 只展示本应用可观测的计数：**今日生成次数、当前并发、全局并发**；无法核实时**不显示**供应商余额、剩余额度等数值，也不宣称对供应商费用硬性封顶（AC-V2-37）。
- `[设计建议]` 三个计数按"当前值／上限"展示并注明"应用侧"；演示图中的数字是虚构样例，真实数值以服务端计数为准，本文不定义额度数值。
- `[补充草案]` 无有效配置时**阻止新的正式生成调用**：发言生成、批注、争点卡、复盘、重练反馈、赛前锦囊；**不阻止**读取历史列表、历史会话详情、已有复盘／批注／争点卡，也不因此删除或隐藏历史（AC-V2-36）。
- `[补充草案]` **"测试连接"不在被阻止之列**：它针对一份完整候选配置显式执行，缺配置只影响正式生成，不限制用户先测再存（测试对象与计费口径见 §7）。
- `[已确认]`（继承既有约束）错因分开提示：配置问题、应用额度／并发、供应商侧错误三类不合并，各自给恢复动作。
- `[待决]` 每日生成次数等额度数值与最长训练赛不匹配的问题见[技术评估 §6](../../planning/PRD_V2_TECHNICAL_ASSESSMENT.md#6-已知额度不匹配)；本节不调整任何额度数值。
