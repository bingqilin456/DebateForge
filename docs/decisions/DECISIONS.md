## ADR-001 后端采用 Gin 的模块化单体

状态：规划采纳，待对应任务实施前人工审查。

背景：原申报书倾向 go-zero，A 已有 Gin 经验，团队需兼顾课程、竞赛及技术学习，业务规模为认证、辩论和历史。优先降低学习、联调和排错成本。

| 方案 | 收益 | 本项目代价 |
| --- | --- | --- |
| Gin 模块化单体 | 复用现有经验，路由与中间件直观，便于追踪完整请求 | 需明确补齐超时、限流、日志、权限、健康与测试，不能把框架等同于生产保障 |
| go-zero 单体 REST | 有代码生成及较完整的工程治理约定，也可只用 REST 层 | 当前需额外学习 goctl、生成代码及配置习惯，收益暂不足以覆盖切换成本 |
| Go 标准库 net/http | 依赖少，控制明确 | 需自行统一路由和工程约定，较难复用 A 的现成 Gin 经验 |

决定：使用 Gin，按 auth、topic、debate、ai 模块组织单个进程，Eino 与框架解耦。Gin 提供路由和中间件机制，go-zero 提供代码生成及治理能力；二者都不能替团队完成业务验收。[Gin 中间件文档](https://gin-gonic.com/en/docs/middleware/)、[go-zero 官方文档](https://go-zero.dev/)

理由是团队熟悉度和 MVP 的交付成本，不是未经测量的性能优劣；也不将 go-zero 等同于必须采用微服务。责任是把必要中间件、事务和异常测试写清并执行。只有后续出现真实服务拆分或统一生成工具需求，且有测量与维护收益时才重新评估，不同时维护两套后端框架。

## ADR-002 前端采用 Vue 3 TypeScript Arco Design

状态：规划采纳，待对应任务实施前人工审查。

沿用项目方向与用户初步技术方案，配合 Vue Router、Vite 和统一 API client。优先用成熟表单、列表和反馈组件；不搭建设计系统、SSR 或动态菜单生成平台。当前页面少，局部状态与轻量共享登录状态足够，暂不强制加入 Pinia。

B 主责辩题与历史页面，A 主导复杂聊天和流式交互。收益是任务可拆分，代价是双方仍需学习 TypeScript、HTTP 和组件状态；不能沿用原申报书“团队已具备扎实 Vue 经验”的陈述。版本组合与必要的测试工具在 T01 核实锁定。

## ADR-003 Eino 仅用于单模型对话

状态：框架方向为规划采纳；不做复杂 Agent 为约束确定。

先使用 ChatModel 完整响应，保留流式适配边界，不引入 Agent Runner、工具调用、RAG、向量数据库或微调。Eino 组件已提供完整及流式响应能力，无需为三轮串行对话创建自主决策循环。[Eino ChatModel 文档](https://www.cloudwego.cn/zh/docs/eino/core_modules/components/chat_model_guide/)

由业务 Service 控制上下文、轮数和数据库，模型只生成内容。供应商通过后端配置指定，采用一个可验证的供应商和模型；不做自动故障切换。代价是供应商故障会使当次生成失败，需要清晰重试入口。具体供应商、模型、额度及输入窗口待确认，不能假设所有“兼容 API”均完整支持结构化输出或流式格式。

## ADR-004 MySQL 与 GORM 并使用版本化迁移

状态：规划采纳，待对应任务实施前人工审查。

采用 MySQL InnoDB 作为开发集成及生产持久化数据库，GORM 负责数据访问；初始表和后续变更用可审查的版本化 SQL，不在生产启动时 AutoMigrate。依靠短事务、外键及唯一索引保证会话、轮次与消息一致，模型调用放在事务之外。[GORM 事务文档](https://gorm.io/docs/transactions.html)

实体为 users、auth_sessions、topics、debates、debate_turns、messages、debate_summaries。独立轮次表用于失败、幂等和恢复，使状态与消息可独立验证。数据库设计见 [ARCHITECTURE](../architecture/ARCHITECTURE.md)，首批 HTTP 契约见 [API](../api/API.md)。

2026 年 11 月 8 日落地增量见 ADR-013：仅六张 Phase 1 表的初始迁移已在隔离测试库技术验证，总结表仍留 T10，种子尚未实施。资源表及历史接入记录中的“迁移未实施”是当时状态。

## ADR-005 同源 Session 认证

状态：规划采纳，待对应任务实施前人工审查。

在单域名、单服务场景使用 MySQL 存储 Session，生产使用 Secure/HttpOnly/SameSite Cookie；随机 token 的哈希入库，退出能立即失效。密码采用成熟 Argon2id 实现。配置独立 CSRF token 和 Origin 校验；不把 Cookie 属性当作全部 CSRF 防线。[OWASP Session 指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

相比 JWT 加 localStorage，这个方案减少浏览器持有可读登录凭据、刷新 token 和吊销列表的工作；代价是请求需查询 Session，需清理过期记录。小规模单体可接受，不为 Session 单独引入 Redis。MVP 不做找回密码和邮件验证，开放范围需结合资源与风控确认。

## ADR-006 普通 JSON 优先 SSE 可选

状态：JSON 优先与后置 SSE 为规划采纳；SSE 非必须来自用户允许。

先验收“鉴权 → AI → 落库 → 展示”的完整响应，在 Phase 3 满足核心门槛且有余量时再选做 SSE。使用带 POST body 的 fetch 消费 SSE 格式，沿用原发送与重试接口；总结继续使用完整 JSON。SSE 为单向流，代理缓冲必须单独处理。[MDN SSE 文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)、[Nginx 代理文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

成功以最终落库为准，断线先查状态，失败才人工重试，不实现事件重放。收益是交付更早、失败路径更简单；代价是第一版有等待时间，需要明确 loading 和超时反馈。若增强未通过代理与断线验收，则关闭 SSE，不拖累 P0。

## ADR-007 三轮业务和总结独立

状态：三轮为约束确定；其余为规划采纳。

用户先发言，AI 持相反立场，完整 AI 回复落库才完成一轮；第 3 轮后辩论 completed。总结用单独请求和状态，前端自动发起、服务端幂等，失败可单独重试。采用 strengths、issues、suggestions 三类结构，不做分数和胜负判定。

相比第三轮和总结串成一次长请求，该方案减少超时后状态不明的问题，也不需常驻任务队列。代价是前端要展示独立总结状态，用户离开页面后可能待下次打开才触发总结。已保存辩论不受总结失败影响。

请求标识、唯一索引、短事务、attempt_version 和过期恢复共同保证数据库结果不重复。2026 年 11 月 1 日审查后，用户授权补齐轮次与总结重试契约：采用 expected_attempt_version，在短事务内仅允许匹配的失败版本认领一次；旧版本请求遇到再次失败返回 409，不重新调用模型，前端也不自动换版本重发。该方案复用现有版本字段，不增加重试表；代价是查询及错误响应须提供当前版本。它们不提供供应商“恰好调用一次”保证，不以隐式自动重试掩盖错误或费用。

## ADR-008 单机 Compose 部署与基本运维

状态：Linux/真实部署/HTTPS/持久化为约束确定；具体部署形态为规划采纳。

使用单台 Linux、Docker Compose、Nginx、单个 Go 实例和 MySQL 持久化卷；公网只暴露 Web 端口。首次公网开放前完成 HTTPS、日志、健康路由、认证限流、输入与生成限额、模型并发/超时检查。真实模型公网试运行另按 ADR-019 验收费用控制并取得单独授权。基本告警、异机备份和独立库恢复按部署及运维计划验收。维持单机架构。

收益是两人能理解并维护完整链路，代价是单机存在故障停机窗口、进程内限额重启丢失，不承诺高可用。历史记录（2026-11-01，健康路径后由 ADR-012 更新，费用门槛后由 ADR-019 更新）。该轮审查后，用户授权把防刷与费用检查前移到 T07 之前，T13 仅做回归与调优；健康端点明确为 `/health/live`、`/health/ready`，由 Nginx 精确代理到 Go 并保留状态与 JSON，不走 SPA 回退。使用供应商硬费用上限和单实例限制控制风险；代价是 Phase 1 工作量增加，未完成检查则推迟公网开放。部署、备份和恢复的实际操作仍须用户明确授权，Phase 0 的 PB 不执行。

## ADR-009 Project Bootstrap 独立验收

状态：2026 年 11 月 1 日用户明确批准，技术验证及人工门槛见 [INIT_ACCEPTANCE](../acceptance/INIT_ACCEPTANCE.md)。

背景：T02 同时包含数据库，T06 包含登录和首轮辩论；直接照表实施会超过本轮授权。因此拆出 PB 作为 T01/T02/T06 的前置任务，不改变 PRD 的最终 P0。

## ADR-014 T02 精确枚举与版本化种子

状态：2026 年 11 月 8 日，用户明确授权，实施及技术验证完成；等待独立审查、辩题人工审阅、负责人验收和学习讲解。完整 T02 未结项。本条为 ADR-013 的后续增量，不替代其目标保护和恢复规则。

选择：00007–00009 每表一个 ALTER，新增 CAST AS BINARY 的精确枚举 CHECK，保留原列类型、约束和六份已执行 SQL。原 ascii_bin 的 PAD SPACE 不能保证持久字符串精确；替代方案修改旧文件会破坏历史，改列类型/触发器超出本轮必要范围。新增 CHECK 校验已有数据，异常即停，不自动 trim。

00010 用单个多行 INSERT 写入固定 ID 1–5，在 Goose 默认事务内同时登记版本。重复 up 在会话锁与前向历史校验下跳过；不另做种子命令或服务启动钩子。替代方案按标题去重缺乏唯一约束，新增业务 key 会改冻结模型；UPSERT/REPLACE/IGNORE 可能覆盖或掩盖 ID 冲突，故选择冲突失败、保留原数据。今后修改题目需新增迁移，人工内容审阅尚未完成。

## ADR-013 T02 独立 Goose 迁移入口与失败保护

状态：2026 年 11 月 8 日用户明确授权本迁移子任务，已完成技术验证及有条件独立审查；负责人已接受验证边界及延期项并授权提交/推送，学习讲解尚未登记。不是完整 T02 结项。

沿用已选 Goose `v3.29.0`，在 `backend/tools/migrate/` 建立独立 Go module 的 CLI，调用官方 Provider 管理 SQL/版本；与标准 Goose 共用 `goose_db_version` 格式。选择独立 module 是为了避免 Goose 要求的 MySQL 驱动 `v1.10.1` 和传递依赖升级服务已锁定的驱动 `v1.8.1`。仅工具新增 Goose（MIT）和成熟 MySQL 驱动（MPL-2.0），版本、用途及替代方案见 [迁移说明](../../backend/migrations/README.md#依赖依据)。服务继续使用 GORM，不引用迁移库，也不在启动时迁移。

保留逻辑实体、HTTP 契约和阶段分工，仅具体化物理类型。每表一个非事务 SQL 版本，六表按依赖建成；总结表留 T10，种子留下一授权闭环。显式 up/status，目标固定为现有 dev/test 回环端口、库和迁移账户；先校验配置再读取秘密，在同一执行连接验证实际身份/MySQL 版本并取得命名锁，按前向版本前缀校验历史。

替代方案与取舍：直接裸用标准 Goose CLI 缺少本项目的同会话目标校验；把 Goose 加到服务 module 会扩大服务依赖变更；手工 SQL 和版本账本易漏记。采用官方 Provider `ApplyVersion`，逐版本加锁和登记，避开 `Up/HasPending` 在加锁前初始化元数据的路径；允许进程在版本边界交替执行。只跳过纯 `ErrAlreadyApplied`，合并的解锁/关闭错误仍失败。

MySQL 单条原子 DDL 仍不与版本登记构成原子事务。不使用 IF NOT EXISTS、Down 或自动修复掩盖故障；部分 DDL 和登记不一致必须核对实际结构，补记版本/数据修复另行审批。Goose 无 SQL 校验和，已执行文件必须保持不可变，后续变更新增版本。失败测试使用独立随机历史/探针表并保留，业务夹具事务回滚；只在测试库执行，开发库未迁移。未实施生产入口、种子、业务 Repository 或其他 T02 子任务，未提交、推送、合并或部署。证据见 [迁移记录](../acceptance/T02_MIGRATIONS_ACCEPTANCE.md)。

2026 年 11 月 8 日验收增量：独立审查未发现 P0/P1；负责人接受两个 P2 和一个 P3 延期，登记于 [TASKS](../planning/TASKS.md#t02-迁移延期问题登记)。枚举 CHECK 必须在业务状态写入前通过新增迁移收紧，不能修改六份已执行 SQL。本轮仅允许将本迁移闭环及验收/风险文档提交并推送到 `origin/feat/t02-database`，不创建 PR、不合并、不推进后续任务。上述“未提交、推送”是实施阶段状态。

## ADR-015 T03 认证实现与 Cookie 名称

状态：2026 年 11 月 8 日，用户明确授权；DSH 实现、Codex 集成技术验证通过，待独立审查与项目负责人人工验收。沿用 ADR-005/T01；未实现其他业务或生产部署。

## ADR-016 T04 Eino 完整响应与预算保护

2026 年 11 月 8 日，按负责人 T04 授权实施；技术实现与无收费验证不代表真实供应商验收或任务结项，当前见 [T04 记录](../acceptance/T04_AI_ACCEPTANCE.md)。旧资源表中的“无 Eino 依赖/模型待定”为历史快照。

模型 Context 上限 45 秒，提供从未来 HTTP 入口开始使用的 60 秒请求辅助函数，保留更短父期限和主动取消。每条输入/辩论回复 1–2000 Unicode 码点，拒绝空白、非法 UTF-8 和超限；保留完整历史，不压缩或截断。以 UTF-8 字节数和消息开销保守预检完整三轮及总结预留，输出 Token 值必须与窗口预检一致，并通过真实请求 JSON 核对；本地输出配置最大 8192 Token，不使用供应商 384K 默认。具体质量参数待受控真实验证。

## ADR-018 T05 首轮认领与单进程准入实现

2026-11-08，依据负责人 T05 实施授权落实冻结契约，不新增 API 字段、错误码或限额；独立审查与人工验收状态见 T05 记录。

选择：本人会话行 FOR UPDATE 串行认领，先核对规范 UUID 和用户原文，再判断首轮与既有记录；非阻塞取得单进程并发槽和每日额度预留后，同一 3 秒短事务写 Turn/user。事务提交后才调用既有 ai.Generator；成功再次锁定会话并按 generating/attempt_version 写唯一 assistant、完成轮数 1，保持 active。失败仅保存受控原因。取消时独立有界 Context 尽力落库。详情使用一致性只读事务，消息按 user/assistant 排序。

资源参数沿用冻结基线：HTTP 从入口先于认证和正文读取设置生成 60 秒、普通 5 秒；模型 45 秒；数据库整个短事务 3 秒。socket WriteTimeout 65 秒兜底，路由实际写期限仍为 60/5 秒。HTTP 6 次/分钟用固定一分钟窗口，20 次/日按 UTC 日界，仅新认领消费；成功/失败均计入，确定回滚返还，提交确认丢失时保守预留。内存最多 20000 用户计数条目，仅回收过期项，不淘汰活跃额度；并发 1/用户、2/Go 进程，不支持跨实例协调和可靠计费，进程重启计数丢失。重放/冲突不占模型槽或每日额度，但仍受 HTTP 分钟防刷。

提交确认未知统一 503、不给出已确认失败 details，查询真实状态且不补发模型。代价是数据库不可用或进程硬崩溃时可能遗留 generating，租约 90 秒字段保留，回收/显式重试由 T09 实现。本轮既不增加后台扫描，也不引入 Redis、队列或新迁移。

安全默认：AI_MODE 空/disabled 不启用真实生成；fake 供无收费联调。显式 deepseek 模式复用 T04 Eino Adapter，必须另获真实调用授权并设置输出 Token 限额；该轮没有修改真实秘密文件或执行真实调用。公网真实试运行当前准入见 ADR-019。

替代方案：持有行锁等待模型会阻塞重放和详情，故不采用；先调用模型再认领会破坏幂等与费用保护，故不采用。分布式配额与持久化费用账本超出单实例 MVP 当前任务，不能将内存计数包装成跨副本全局保证。

## ADR-019 受控公网模型费用准入

2026-11-09，项目负责人确认。替代 ADR-008/017 中「必须有供应商硬预算才能开放公网真实模型入口」的旧门槛。T04 已执行的一次本地例外及其精确结算未知的历史结论继续适用。费用任务和验证细目统一登记于 [T07-COST-01](../planning/TASKS.md#t07-cost-01-供应商硬预算缺失)。

## ADR-020 Phase 2 采用基于现有文档与 CI 的轻量 SDD 工作流

2026-11-11，按项目负责人要求为 Phase 2（`T08`～`T12`）建立轻量级 Spec-Driven Development（SDD）工作方式。本轮仅建设工作流与必要文档，不启动 Phase 2 实际功能开发。

背景：Phase 1（`T01`～`T07`）已完成本地结项，且仓库已在 `.github/workflows/ci.yml` 建立包含静态规范、前后端单测与构建、隔离 MySQL `8.4.13` 迁移及集成测试的自动化门禁。Phase 1 期间曾出现计划文件命名不统一、每次子任务在多份顶层文档顶部叠加状态快照横幅、以及在 CI 上线前于验收文档中重复记录大量常规静态/单测输出的问题。Phase 2 需要更聚焦、低摩擦的规范驱动开发流程。

决定：采用「Phase 管理里程碑、功能任务驱动开发、Spec 明确需求、CI 负责基础质量」的轻量 SDD 模式，完整规范与 `T08`～`T12` 拆解基线集中维护在 [Phase 2 轻量 SDD 工作流](../planning/PHASE2_SDD_WORKFLOW.md)：

1. **复用既有单一事实来源**：以 [PLAN](../planning/PLAN.md) 管理阶段里程碑，[TASKS](../planning/TASKS.md) 作为任务状态的唯一主入口，[PRD](../product/PRD.md)、[ARCHITECTURE](../architecture/ARCHITECTURE.md)、[API](../api/API.md) 与 [OpenAPI](../api/openapi.yaml) 作为全局契约，[AGENTS](../../AGENTS.md) 作为协作与安全红线。
2. **单文件轻量任务 Spec**：每个任务获准实施时，在 `docs/planning/Txx_<SLUG>_SPEC.md` 编写单文件增量 Spec（明确范围、API/迁移增量、状态不变量、实施 Slice 与验收矩阵），并将落地的 Phase 2 草案接口晋升至 `API.md` 与 `openapi.yaml`。
3. **CI 守住基础质量，Acceptance 聚焦专项证据**：由 `.github/workflows/ci.yml` 自动承担格式、链接、单测、隔离 MySQL 集成和前端构建门禁；`docs/acceptance/Txx_<SLUG>_ACCEPTANCE.md` 仅聚焦业务 AC 验证、并发 `-race`/真实浏览器专项证据与负责人验收结论，不要求强制重复独立审查或无关全量复跑。

替代方案与取舍：引入外部完整 Spec Kit（如 `.specify/` 多文件模板、专用生成 CLI 或独立 `specs/` 目录树）会与现有 `PRD.md`、`ARCHITECTURE.md`、`API.md` 形成双轨重复维护，增加同步负担，故不采用；完全不写任务级 Spec 直接编码则容易在 `T09`/`T10` 的版本冲突、租约回收和 Schema 校验边界上遗漏约束，故采用单文件增量 Spec 折中方案。
