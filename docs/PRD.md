# 思弈阁 Lite 产品需求

初版：2026 年 11 月 1 日；2026 年 11 月 2 日同步阶段制用语，11 月 7 日同步验收流程简化。文中 P0 是必须交付的优先级，Phase 0 是工程初始化与基线验收阶段。当前进度见 [PLAN](PLAN.md)。

## 背景与目标

思弈阁 Lite 为缺少练习对手的中文辩论初学者提供短时文字练习和复盘反馈，也是双人团队用于 AB 实验室复试、按阶段目标推进的工程项目。成功标准是用户能在真实服务器上完成一场辩论、查看持久化历史和结构化建议，开发者能解释系统实现、测试与运维方法。

原申报书提供 AI 辩论、Vue 3、Arco Design、Go 和 Eino 的方向参考。本次正式选定思弈阁并允许缩减范围；以本次需求、当前团队能力和 MVP 范围为约束，不承担原申报书的长期研究、预算和大规模并发承诺。资料读取与差异记录见 [DECISIONS](DECISIONS.md)。

## 用户与真实场景

- 主要用户：希望练习论证的中文初学者。空闲时选一个预设辩题，选择正方或反方，在数分钟内完成三轮对话，获得有针对性的改进建议。
- 回访用户：登录后打开历史记录，复盘某轮发言和 AI 反驳；未完成的辩论可以继续，不要求从头开始。
- 评审与维护者：复试时验证公网访问、权限隔离、AI 错误处理、数据重启后保留及备份恢复，并询问两位成员的技术决策。维护操作通过受控服务器工具完成，不另做后台管理页面。

不把 AI 建议作为客观裁判或事实核验。页面明确说明内容由 AI 生成，仅供练习参考，避免输入个人敏感信息。

## 功能边界与优先级

| 编号  | 功能              | 优先级 | 范围                                   |
| --- | --------------- | --- | ------------------------------------ |
| F01 | 注册、登录、退出、登录状态恢复 | P0  | 用户名和密码，不收集手机号、邮箱或学号                  |
| F02 | 预设辩题与正反立场       | P0  | 至少 5 个经人工审阅的中文辩题，无用户自建辩题             |
| F03 | 三轮文字辩论          | P0  | 用户先发言，AI 自动持相反立场；每轮一条用户消息和一条完整 AI 回复 |
| F04 | 会话和消息持久化        | P0  | 仅本人可见，可恢复未完成会话，历史列表分页                |
| F05 | 结构化 AI 总结       | P0  | 三轮完成后生成论证优点、问题、改进建议；保存并可重读           |
| F06 | 失败与重复请求处理       | P0  | 超时提示、显式重试、刷新恢复、不重复计轮或写消息             |
| F07 | 公网交付与基本保障       | P0  | HTTPS、持久化 MySQL、限流、日志、健康检查、备份恢复、基本监控 |
| F08 | SSE 流式回复        | P1  | 普通请求链路稳定后再做，可不纳入 MVP 交付                  |

P0 表示最终验收必需，各阶段按 [PLAN](PLAN.md) 的目标与门槛推进，不规定固定自然日工期。P1 是增强项，缺席不阻塞 MVP 验收。

明确不做：语音、多模态、多人实时辩论、排行榜、支付、社交、复杂评分体系、多 Agent、知识图谱、RAG、向量数据库、模型训练或微调、微服务、Kubernetes。账号找回、邮箱验证、个人资料管理、历史删除与导出、辩题管理后台也不纳入本次 MVP。不能把非目标作为“顺手做”的新增工作。

## 核心用户流程

1. 用户注册后登录，查看预设辩题，选择自己的正方或反方立场。
2. 创建辩论会话，固定辩题、立场和三轮上限。此时不调用模型，AI 也不主动开场。
3. 用户发送第一条发言；界面进入等待状态，禁止连点提交。AI 依据辩题、相反立场及本场上下文回复。
4. 完整 AI 回复保存成功后，完成轮数增加 1，再允许下一轮。第三轮完整回复保存后，辩论状态变为 `completed`，不再接收第四轮。
5. 前端自动发起独立的总结请求。总结成功后展示三类反馈及对应轮次；失败则保留全部辩论，展示重试入口。第三轮回复与总结不放在同一个长请求里。
6. 返回历史列表，能打开原会话、六条正式消息和已保存总结。未完成会话可继续；存在失败轮次时先处理该轮，不能跳到下一轮。

用户刷新或关闭页面不会删除已保存内容。正在生成的请求先查询状态；已成功则直接读取，失败才由用户明确重试。网络失败可能产生供应商计费，系统不承诺模型调用恰好一次。

## 业务规则

- “三轮”严格指三组用户与 AI 消息，正常结束恰好 6 条正式消息；总结独立保存，不计入轮次。
- 用户立场为 `pro` 或 `con`，AI 立场由服务端反转。辩题、立场及规则在会话创建后不能修改。
- 新轮次只能是当前已完成轮数加 1。AI 失败时保留这轮用户原文和失败状态，不增加完成轮数、不生成伪造 AI 消息；重试复用原文和同一轮次。
- 同一个请求标识重复提交不能重复写消息或推进状态；两次并发提交不能同时占据同一轮次。轮次和总结重试均须绑定用户已看到的失败版本；一次重试再次失败后，旧版本重复请求不能再次调用模型，须由用户查询最新状态并明确发起新的重试。具体约束见 [ARCHITECTURE](ARCHITECTURE.md)。
- 已完成辩论不能续聊或重写历史；要重新练习需创建新会话。未完成会话暂不提供提前结束并生成总结。
- 总结包含 `strengths`、`issues`、`suggestions` 三个非空数组，条目引用用户轮次 1 至 3。问题与建议应有具体依据，不做胜负排名或总分。
- 初始假设：单次用户发言 1 至 2000 个 Unicode 字符，单条 AI 回复最多 2000 个 Unicode 字符；服务端同时设置 token 上限并校验结果，不能把 token 等同于字符。

## 可验证的验收标准

| 编号   | 条件与操作                              | 通过标准                                                         |
| ---- | ---------------------------------- | ------------------------------------------------------------ |
| AC01 | 注册新用户名，再尝试重复注册、错误密码、退出后访问          | 注册成功；重复注册 409；登录失败 401；退出后的原 Session 不再有效；数据库无明文密码           |
| AC02 | 登录后浏览辩题并分别选择正反立场                   | 至少 5 个辩题；创建后返回固定题目及双方相反立场；非法立场或不存在辩题被拒绝                      |
| AC03 | 连续提交三轮，随后尝试第四轮                     | 每轮仅一条用户消息和一条完整 AI 回复，轮数依次为 1、2、3；第四轮 409 且数据库不变              |
| AC04 | 第 2 轮模拟超时，再重试；并发发送同一轮              | 完成轮数仍为 1；失败状态和原文可见；显式重试成功后为 2；没有重复消息或并发多计轮；重试再次失败后重发同版本请求为 409，不增加模型调用或生成额度；期望版本缺失/非法为 400                   |
| AC05 | 模拟响应丢失后重发同一请求标识，并在生成期间重启服务         | 已完成结果被复用；进行中可查询；残留生成状态在过期恢复窗口内变为可重试，迟到结果不能覆盖新尝试              |
| AC06 | 第三轮完成，检查总结；模拟非法 JSON 或供应商失败        | 三个数组均通过结构校验且各至少一项，轮次引用合法；无效结果不作为成功总结；失败可重试且辩论仍在；总结重试再次失败后重发旧版本为 409，不增加模型调用或生成额度              |
| AC07 | 完成辩论后刷新、退出重登并重启应用和数据库容器            | 本人的会话、正式消息、总结仍可读，未完成会话可继续；重启不删除数据卷                           |
| AC08 | 用户甲访问用户乙的会话、轮次和总结接口                | 列表不含他人数据；详情、发送、重试、总结统一返回 404，不泄露是否存在                         |
| AC09 | 在公网实际完成注册、三轮、总结、重登和历史查询            | 首次公网开放前已验证认证限流、请求体/字符限制、生成次数/并发/超时及供应商硬预算；有效 HTTPS，无证书警告或 Mixed Content；生产使用 MySQL，无浏览器直连模型；主流程全部通过    |
| AC10 | 检查安全、可观测性及恢复演练                     | CSRF、输入长度、限流有验证记录；日志可关联 request_id 且无敏感正文；经公网 Nginx 查健康端点返回约定 JSON，DB 不可达 ready=503，Go 停止为非 2xx 或连接失败，HTML 200 不算健康；独立环境成功恢复备份 |
| AC11 | 核对交付说明与失败路径验证记录               | 交付说明覆盖模块职责、关键链路及失败路径，验证记录可追溯；开发成员在实施中理解各自负责的模块，无需正式契约讲解或 A/B 互审登记           |
| AC12 | 若交付 SSE，经过 Nginx 测试 UTF-8 分块、断线和刷新 | 逐步显示增量；仅持久化成功后报告完成；断线后查询恢复且不重复调用模型；否则不宣称交付 SSE               |

自 T01 起，保留 Codex 技术审查、必要的自动化测试与项目负责人最终验收；安全、数据正确性、真实模型费用等高风险事项仍须专项验证。验收流程调整依据见 [ADR-011](DECISIONS.md#adr-011-简化验收流程与-t01-结项)。

AI 质量采用人工检查：由 T14 负责人组织评估至少 5 场完整对话，覆盖至少 3 个辩题及正反立场；检查是否回应用户观点、保持相反立场、建议是否具体。保存匿名化结论和失败样例，不把语言模型输出当作确定性断言。

## 运行目标与假设

面向小范围试用，初始容量假设为 10 个同时在线用户、全局最多 2 个并发模型调用，不承诺互联网大规模服务。首版普通 API 在上述负载下目标 p95 小于 500 ms，排除模型调用、密码哈希及外网波动，并在验收记录中注明测试环境。

单次模型调用暂定 45 秒超时，单个生成请求总预算 60 秒；超过预算明确失败，不无限等待。流式不改变总预算。服务器与供应商实测后可通过 ADR 修订参数。

待确认问题集中在 [DECISIONS 的假设登记](DECISIONS.md#假设与待确认问题)：可投入工时、模型与费用、服务器与域名、开放范围与数据保留。默认方案可用于继续评审，但不代表已获得资源或部署授权。
