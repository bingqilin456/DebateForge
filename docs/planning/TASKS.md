## 分工、估算与依赖规则

A 负责契约、Go/Gin、Eino、MySQL、安全、部署和复杂聊天交互；B 负责可拆分的常规页面、真实联调、场景测试及说明资料。B 独立完成并理解辩题和历史至少两个页面，A 提供接口边界与协助；关键安全测试不完全交给初学者。可因课程、考试或竞赛调整分工，记录交接和模块责任，不把 B 的贡献缩减为只准备演示材料。

S 为低复杂度，约 1–3 人时；M 为中复杂度，约 3–6 人时；L 为较高复杂度，约 6–10 人时，应按子边界小步交付。人时是开发、学习、AI 输出理解审查与验证的粗略工作量估算，不是自然日或完成期限；不要求成员固定投入时长，实际投入可灵活调整，超出估算不降低验收标准。协作时间单列，不把两人并行视为零成本；原 T01–T18 的复杂度与估算保留。PB 原来未估工，本次只粗估剩余人工审查与讲解，不追填已发生工时。

所有任务均须满足所属阶段的前置门槛及授权范围。表中列明任务依赖与联调条件；只要依赖满足，可在阶段内选择独立任务或分工并行，不要求按编号依次完成。并行组 P-A 为契约后的基础模块，P-B 为核心闭环，P-C 为质量工作；同一成员的实际投入、共享文件和 API 变更必须协调。提前准备限于已确认契约下的页面、测试场景或文档，不跳过真实联调和独立验收，也不据此跨阶段扩大实施。

### T07-COST-01 供应商硬预算缺失

**未关闭，仍阻塞真实模型公网试运行。** 负责人于 2026-11-09 撤销供应商级硬预算作为唯一绝对 P0 门槛。若 DeepSeek 无法提供满足要求的硬上限，可按 [ADR-019](../decisions/DECISIONS.md#adr-019-受控公网模型费用准入) 使用经验证的替代控制。负责人接受无法绝对封顶的残余风险。T07 部署准备版仍只允许 `disabled` 或 `fake`。

**已实现且有证据。** T04 有保守的完整 Prompt 窗口预检、显式输出 Token 限额、模型 45 秒与请求 60 秒预算及受控失败。T05 有每用户 6 次/分钟 HTTP 防刷、UTC 日 20 次新生成尝试、单用户并发 1、单进程并发 2。失败尝试计数，重放和冲突不重新生成。进程内计数重启可丢失，无法充当全站费用账本。T04 一次本地真实调用授权已消耗，精确结算费用未知。 [T04 验收](../acceptance/T04_AI_ACCEPTANCE.md#最终人工验收与结项) · [T05 验收](../acceptance/T05_FIRST_TURN_ACCEPTANCE.md#最终人工验收与无收费范围结项)

**2026-11-14 控制范围收窄（[ADR-022](../decisions/DECISIONS.md#adr-022-费用治理充值硬顶兜底与最小化控制子集)）。** 负责人确认采用「充值硬顶兜底 + 最小控制子集」：保留 `01A`（全站次数与 Token 预算）与 `01B`（自动熔断、紧急停用、跨重启保持停用）作为公网开放前置；`01C`/`01D` 降级为按需验证，其中 `01D` 的「无隐式自动重试」一条仍须在真实公网试运行前确认。平台充值余额作为绝对兜底，但它是**总量闸而非速率闸**——进程内计数重启即重置，突发流量仍可能在极短时间内耗尽余额。**本方案不提供供应商级绝对费用封顶**，该残余风险由负责人接受并记录在此。

| T07-COST-01C · 监控与对账 | 区分预留、供应商返回用量、费用估算、可核对结算及余额，明确数据延迟/未知值。用假数据验证阈值告警、采集失联和延迟账单，记录接收与处置演练。使用真实账户或供应商证据须另获授权，全程脱敏。 |
| T07-COST-01D · 重试与在途 | 默认一次尝试仅允许一次供应商请求。检查应用、SDK、传输与代理的自动重试和故障切换路径，以计数桩覆盖超时、429/5xx、连接异常、客户端取消、结果不明与重放。熔断只保证拒绝新准入，验证在途上限和最大已预留敞口，保留取消后继续计费及延迟结算风险。将来任何获准的新尝试均须重新准入与计入预算。 |

允许因课程、考试或竞赛暂停，或暂时搁置技术阻塞任务；保留已验收成果、在途改动及证据，不清零或强制追赶。恢复时仅检查当前 Phase、已完成且通过验收的任务、进行中/待人工验收任务、未解决阻塞、下一项满足依赖和授权的任务。负责人调整同步交接记录；环境或契约变化时重验受影响项。

## 任务执行模板

Phase 2（T08–T12）具体执行细则与 Spec 模板见 [Phase 2 轻量 SDD 工作流](PHASE2_SDD_WORKFLOW.md)：

1. **Spec 确认与契约对齐**：按需读取相关 PRD、架构与上游契约，核对阶段门槛、任务依赖、工作区和授权范围。编码前在 `docs/planning/Txx_<SLUG>_SPEC.md` 明确本任务增量边界、状态转换与验收矩阵；涉及 Phase 2 草案接口落地时同步晋升至 [API](../api/API.md) 与 [OpenAPI](../api/openapi.yaml)。
2. **测试先行（RED）**：先明确输入、输出、权限、状态、失败路径与测试并观察预期失败；业务风险用 Fake 或隔离 MySQL 验证，文档或样式改动只做对应检查。
3. **最小交付与分片推进（GREEN）**：实现最小交付，按改动影响范围运行相关定向测试、类型/构建和真实联调，直接复用未受影响的既有证据，不做无关全量复跑或无意义复验。L 任务按 Spec 子切片（Slice）小步验证（例如 T09 分三轮规则、重试并发、崩溃恢复），不为覆盖率堆测试。
4. **CI 基础门禁与专项验收**：由 [.github/workflows/ci.yml](../../.github/workflows/ci.yml) 守住静态规范、单测、隔离 MySQL 集成及前端构建等基础质量；完成必要的自动化测试及相关高风险专项验证，在 `docs/acceptance/Txx_<SLUG>_ACCEPTANCE.md` 简明记录文件范围、环境、命令与结果、未执行项和遗留问题。验证完成后仅在本文件置“待人工验收”，经项目负责人确认后置“已完成”；不要求 A/B 互审、正式契约讲解登记或强制重复独立审查，不再向多份顶层文档叠加状态快照横幅。
5. **授权边界**：未经明确授权不 commit、push、合并或部署。任务完成不自动进入下一阶段；阶段末报告验证结果、遗留问题及下一阶段前置条件，等待负责人确认。

## 责任不能转交给 AI

A 在实施中理解 Handler/Service/Repository、数据库唯一约束、短事务、attempt_version、Eino 上下文、超时、权限与恢复；B 在实施中理解组件状态、props/事件、API 请求、登录失效、分页与失败提示。两人共同理解**赛制语义（`debates.mode` 为唯一事实来源、`standard_4` 与 `quick_3` 的轮数差异、第 3 轮环节分叉）**、数据归属和上线风险。

如 B 可投入精力下降，优先保持 T08 与 T11 的独立开发和模块理解，减少 T14/T18 的排版工作，由 A 接管 T06 的更多集成。不能把 B 的技术贡献压缩为只运行 AI 命令或准备演示文稿。
